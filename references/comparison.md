# Сравнительный UX-аудит — правила

Используй этот файл, когда дизайнер просит сравнить два и более концепта/варианта/итерации. Сравнение — отдельный режим скилла, с отдельным шаблоном и скриптом сборки.

---

## Правило 1. Нумерация концептов

Концепты всегда нумеруются: **«Концепт 1», «Концепт 2», «Концепт N»**.

Никогда не использовать: «A/B», «Вариант 1/2» (если дизайнер сам не сказал «вариант»), «Старый/Новый», «Исходник/Доработка» — это создаёт ложную иерархию.

Если дизайнер сам называет концепты иначе («новая версия», «v2», «прежний», «улучшенный») — можно использовать его термины. Если нейтральные имена файлов (Goods_1.jpg, Concept_A.png) — переводим в нумерацию.

---

## Правило 2. Определение режима сравнения

Два режима — параллельный и итеративный. Они влияют на формат блоков выводов.

| Сигнал в запросе | Режим |
|---|---|
| «было/стало», «до/после», «доработал», «новая версия», «v2 экрана», «исправил», «улучшил» | **Итеративное** |
| «сравни», «два варианта», «какой выбрать», «оцени оба», нейтральные имена файлов | **Параллельное** |
| Не указано явно | **Параллельное по умолчанию** |

**Чем режимы отличаются на практике:**

| Элемент | Параллельный | Итеративный |
|---|---|---|
| Заголовок | «UX-сравнение: Концепт 1 vs Концепт 2» | «UX-сравнение: было → стало» |
| Блоки выводов | «Сильные стороны 1 / Сильные стороны 2» | «Что улучшилось / Что осталось / Новые риски» |
| Финал | Гибридная рекомендация или выбор | Рекомендация по следующей итерации |

В обоих режимах структура таблицы одинаковая.

---

## Правило 3. Структура таблицы сравнения

7 колонок (та же логика, что в одиночном аудите, плюс одна колонка «Сравнение»):

| Тип | Эвристика | Сравнение | Проблема | Риск | Критичность | Что сделать |

**Колонка «Сравнение»** — лаконичная метка без избыточных слов:
- `✓ Концепт 1` — если по этой эвристике Концепт 1 лучше
- `✓ Концепт 2` — если по этой эвристике Концепт 2 лучше
- `✓ Концепт N` — для большего числа концептов
- `⚖ Паритет` — если разницы нет или эвристика «всё хорошо» в обоих

Слово «лучше» в метке не нужно — название колонки «Сравнение» уже задаёт контекст.

**Градация преимущества цветом** (без изменения текста):
- Если эвристика 🔴 Высокая или 🟠 Средняя и один концепт её решает — бейдж **насыщенного цвета** (CSS-класс `strong`). Это сигнал: концепт решил серьёзную проблему.
- Если эвристика 🟡 Низкая и один концепт её решает — бейдж **приглушённого цвета** (CSS-класс `soft`). Сигнал: преимущество есть, но небольшое.
- 🟢 Нулевая или Паритет — всегда серый.

Скрипт `build_compare.py` определяет класс автоматически по полю `criticality` в JSON, дополнительные данные не нужны.

**Колонка «Тип»** — в сравнительной таблице **иконка + слово** (`🤔 Непонятно`, `⛔ Ошибки`). В одиночном аудите оставляем только иконку — здесь даём слово, потому что таблица шире и слово быстрее считывается.

**Колонка «Проблема»** — формула гипотезы с привязкой к конкретному концепту:
- Если один концепт лучше: «В Концепте N пользователь может…, потому что…, из-за чего…»
- Если паритет: «В обоих концептах пользователь может…»
- Если оба «всё хорошо»: «Проблем не выявлено — оба следуют конвенциям…»

**Колонка «Что сделать»** — что использовать в финальной версии или следующей итерации:
- При выигрыше одного: «Использовать решение Концепта N: …»
- При паритете: «Добавить … в обе версии»
- При паритете-«всё хорошо»: `—`

## Правило 4. Подсчёт % для каждого концепта

Используется формула одиночного аудита (🟢=10%, 🟡=7%, 🟠=3%, 🔴=0%). **Каждый концепт оценивается независимо** — у каждого своя критичность по каждой эвристике. Это гарантирует, что **оценка концепта в сравнении совпадает с оценкой того же концепта в одиночном аудите** (один и тот же экран не может иметь две разные оценки).

В JSON для сравнения используется поле `criticalities` — массив критичностей по индексам концептов:

```json
{
  "heuristic": "8. Эстетика",
  "criticalities": ["🟡 Низкая", "🟢 Нулевая"],
  ...
}
```

Тогда:
- Концепт 1 получает 7% за эвристику (🟡)
- Концепт 2 получает 10% (🟢)

Колонка «Сравнение» (✓ Концепт N / ⚖ Паритет) выводится **автоматически** из массива `criticalities` — у кого критичность лучше, тот «winner». Колонка «Критичность» в таблице показывает критичность у проигравшего концепта (она же — критичность решаемой проблемы).

Если в JSON указан только устаревший формат (`criticality` + `comparison` без массива) — скрипт использует упрощённую логику для обратной совместимости, но это менее точно.

Итог по 10 эвристикам — % для каждого концепта. Скрипт `build_compare.py` подсчитывает автоматически.

Победитель в верхней плашке — у кого выше %. Если разные оценки — лучший выделяется зелёным цветом. Если совпадают — никого не выделяем, добавляем гибридную рекомендацию.

## Правило 5. Поддержка N концептов

- **2 концепта** — миниатюры в 2 колонки, таблица с 7 колонками.
- **3 концепта** — миниатюры в 3 колонки, в колонке «Сравнение» возможны значения `✓ Концепт 1/2/3 лучше` + `⚖ Паритет`.
- **4 концепта** — те же 4 колонки, но макет уже плотный. Скрипт предупреждает.
- **5+** — не рекомендуется в одном артефакте. Делить на пары (Концепт 1 vs Концепт 2, Концепт 3 vs Концепт 4).

Цвета концептов в колонке «Сравнение» — заранее заданы в шаблоне:
- Концепт 1 — синий
- Концепт 2 — фиолетовый
- Концепт 3 — янтарный
- Концепт 4 — бирюзовый

Это нейтрально-разные оттенки, без «зелёный = хорошо / красный = плохо».

## Правило 6. Структура HTML-артефакта сравнения

Сверху вниз:

1. **Шапка** — заголовок, мета-описание, кнопки PDF/JPEG
2. **Верхняя плашка-вердикт** — оценки в %, победитель выделен зелёным цветом, одна строка вывода. **Всегда наверху, чтобы дизайнер видел итог за 3 секунды**
3. **Превью концептов** — миниатюры в N колонок
4. **Таблица сравнения** — 10 эвристик в 7 колонках
5. **Сильные стороны каждого концепта** — N карточек (только для параллельного режима). Заголовок каждой карточки: `Концепт N` + оценка `N%` серым справа (без дублирующих слов «Сильные стороны»)
6. **Гибридная рекомендация** — если уместно, отдельный блок
7. **Дисклеймер** — если есть встроенные скрины

Для **итеративного режима** блок «Сильные стороны» заменяется на три блока: «Что улучшилось», «Что осталось», «Новые риски».

---

## Правило 7. Гибридная рекомендация

Часто финальная версия не «концепт 1 или 2», а **композиция**: «возьми структуру из A, плотность из B». Это особенно ценно при равноценных концептах.

**Когда уместна гибридная рекомендация:**
- Один концепт сильнее по логике, другой — по визуалу
- У каждого есть уникальная сильная сторона
- Оба имеют общие нерешённые проблемы

**Когда не уместна:**
- Один концепт безусловно слабее (нет смысла «брать оттуда что-то»)
- Концепты основаны на принципиально разных моделях взаимодействия

В JSON для скрипта поле называется `hybrid_recommendation`. Если не указано — блок не выводится.

## Правило 8. Запуск скрипта сборки

```bash
python3 /path/to/skill/references/build_compare.py \
  --data /tmp/compare-data.json \
  --template /path/to/skill/references/html-template-compare.html \
  --output /mnt/user-data/outputs/ux-compare-<name>.html
```

Структура JSON — в начале файла `build_compare.py`. Поля:

- `title` — заголовок (стр.)
- `meta` — мета-описание (стр.)
- `concepts[]` — массив концептов: `screenshot_path`, `caption`, `subcaption`, `strengths[]`
- `no_screenshots` — bool, для NDA-режима
- `top_conclusion` — вывод одной строкой для верхней плашки (можно `<strong>` теги)
- `rows[]` — 10 строк таблицы. Для каждой:
  - `type_icon`, `type_label` — иконка типа влияния + слово
  - `heuristic` — название эвристики
  - **`criticalities`** — массив критичностей по концептам (`["🟠 Средняя", "🟢 Нулевая"]`). **Это основной формат.** Колонка «Сравнение» и колонка «Критичность» выводятся из него автоматически.
  - `problem`, `risk`, `action` — текст ячеек
  - (опц.) `comparison`, `criticality` — устаревшие поля для обратной совместимости; если не указаны, выводятся из `criticalities`
- `hybrid_recommendation` — текст гибридной рекомендации (опционально)

Скрипт сам подсчитает оценки, определит победителя, соберёт CSS-классы и блоки.

**Валидация согласованности текста и автоподсчёта.** Скрипт проверяет, что проценты в `top_conclusion` (в формате `N%`, диапазон 40–100) совпадают с реально посчитанными оценками концептов. Если есть расхождение — выводит предупреждение в `stderr`:

```
⚠️  ВНИМАНИЕ: расхождение между текстом и автоподсчётом
   В top_conclusion упомянуты: 84%, 70%
   Скрипт посчитал реальные оценки: 73%, 94%
   Возможно, текст вывода устарел или написан до правки criticalities.
   Обновите формулировку в JSON, чтобы числа сошлись.
```

Маленькие проценты (например, «на 20% больше») не вызывают ложных срабатываний — порог 40% отсекает их. Это защищает от того, что текст-вывод писался руками до прогона скрипта и устарел после правок критичностей.

## Правило 9. Экспортные стили (PDF / JPEG)

При нажатии на кнопку «Скачать PDF» или «Скачать JPEG» в шаблоне активируется класс `body.exporting`, который меняет визуал на момент рендера:

1. **Скрытие кнопок** — `.actions` становится `visibility: hidden`, чтобы кнопки не попали в файл.
2. **Белая рамка 24 px** вокруг контента — `#audit-root` получает `padding: 24px` и `background: #fff`.
3. **Фиксированная широкая ширина** — `#audit-root` становится 1700 px (сравнение) или 1500 px (одиночный), как на десктопе, чтобы текст в ячейках переносился нормально, а не растягивался в одну строку.
4. **Разворот таблицы** — `.table-wrap { overflow: visible }`, чтобы вся таблица попала в файл без обрезки правого края.
5. **Фиксированные ширины колонок** — `table-layout: fixed` + явные `width` для всех `col-*`. Колонки «Проблема» и «Что сделать» получают одинаковую ширину **440 px** — в обоих режимах (одиночный и сравнение). Это даёт консистентный визуальный ритм текста между разными артефактами.
6. **Переносы в бейджах сравнения** — на крайний случай длинных меток `white-space: normal` разрешает перенос внутри ячейки.

PDF собирается через `html2canvas` (рендер DOM в canvas) + `jsPDF` (canvas → PDF многостраничный A3 landscape). Скачивание через `pdf.output('blob')` + `<a download>` — это **обходит ограничение sandbox Claude.ai**, где стандартный `pdf.save()` блокируется CSP.

JPEG — через `canvas.toBlob('image/jpeg', 0.92)` + `<a download>` тем же способом.

## Когда переходить из markdown в HTML для сравнения

В одиночном аудите markdown — дефолт. Для сравнения **всегда HTML** — потому что:

1. Превью двух концептов рядом — это основа сравнения, в markdown их не покажешь
2. Таблица из 7 колонок в markdown совершенно нечитаемая (узкие колонки)
3. Сильные стороны в N колонок — нужна grid-вёрстка

Исключение: дизайнер явно сказал «сравни кратко» или «без файла». Тогда markdown с компромиссами:
- Превью не вставляем (упоминаем в тексте «Концепт 1 — Goods_1.jpg, Концепт 2 — Goods_2.jpg»)
- Таблица в 5 колонок: Эвристика, Сравнение, Проблема, Критичность, Что сделать (Тип и Риск — выкидываем)
- Сильные стороны — простыми списками
